# 스킬 평가

스킬 하나의 트리거 정확도와 품질 델타를 실제 실행으로 측정한다.

## 절차는 스크립트가 한다

실행·반복·파싱·집계는 전부 결정적이므로 직접 하지 말고 이 스킬에 번들된 스크립트를 부른다.
아래의 `<eval>` 은 실행 환경에 따라 고른다:

- soohan-skills 체크아웃 안: `pnpm eval`
- 그 외 어디서든: `npx -y tsx <이 SKILL.md 가 있는 디렉터리>/scripts/cli.ts` — Node 만 있으면 된다

```bash
<eval> mine   <스킬>   # 로그 채굴 → cases.draft.jsonl  (수십 초~1분, 원본 수에 비례)
<eval> record <스킬>   # 실행 → 런 디렉터리 적재  (--runtime=claude|codex, --resume=<runId>, 특정 케이스 재측정 --case=<id,…>)
<eval> judge  <runId>  # 페어와이즈 판정
<eval> report <runId>  # 표 출력
```

`<스킬>` 지정: `plugin:skill` id 를 넘기는 것이 기본이다. 이 순서로 찾는다 —

1. 체크아웃 안의 `plugins/<plugin>/skills/<skill>` (그 파일을 고치는 중이면 이쪽을 재야 한다)
2. 설치된 사본. Claude Code 의 설치 기록에서 **지금 프로젝트에 깔린 버전**을 골라
   `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/skills/<skill>` 로 간다.
   세션이 실제로 읽는 사본이 그것이므로 그것을 재는 게 맞다.

버전이 디렉터리 이름이라 재설치할 때마다 경로가 바뀌므로, 경로를 손으로 넘기는 것보다 id 가
안전하다. 그래도 경로를 직접 주고 싶으면 `…/<plugin>/skills/<skill>` 모양이면 되고, 플러그인
이름은 `plugin.json` 에서 읽으므로 버전 칸에 커밋 SHA 가 와도 상관없다.

해석 결과에 SKILL.md 가 없으면 실행 전에 멈춘다 — 존재하지 않는 스킬을 재면 발동률이 0% 로
나오고 `forced` 가 없는 슬래시 커맨드를 부른다.

결과는 체크아웃 안이면 레포 `evals/`, 밖이면 `~/.skill-eval/` 에 쌓인다.

## 돌리기 전에 갖춰야 할 조건

**격리는 하네스가 한다 (Claude Code 런타임).** 레코딩은 실행(재시도 포함)마다 새 빈 임시
디렉터리를 cwd 로 파고, 유저 스코프 설정을 제외한다(`--setting-sources project` — 전역
플러그인·훅·유저 CLAUDE.md 차단. 실측 2026-07-29: 스킬 66→23개, OAuth 유지. 도입 전에는
트리거 실패 10건 중 9건이 전역 브레인스토밍 훅에 턴을 뺏겼다). 트리거 축은 **격리(진공)
발동률**이다 — 그 계정의 실환경 발동률이 아니다. 나머지 환경은 변형마다 다르다 (실측 2026-07-30):

- `with` — 대상 플러그인 전체를 로드(`--plugin-dir`)하고 **2턴**을 준다. 첫 턴을 폴더
  정찰에 쓰고 잘리는 부류가 1턴 측정에서 통째로 미발동 집계됐기 때문이다(실측 54런 중 47런).
  리포트가 발동을 "즉시/정찰 후"로 갈라 보여준다. 플러그인이 훅을 실으면 그 훅도 함께 돈다 —
  이 경우 트리거 축은 description 단독이 아니라 **플러그인 전체(훅 포함) 발동률**이고
  리포트에 그렇게 라벨된다.
- `forced` — SKILL.md 본문을 프롬프트에 직접 주입한다. `-p` 모드의 슬래시 커맨드는 "로드했다"
  고만 하고 본문을 컨텍스트에 넣지 않는 실측 때문이다(격리 전에는 계정의 넓은 권한이 모델의
  자가-읽기 폴백을 몰래 지탱했다). `--add-dir` 로 플러그인 디렉터리를 열어 참조 파일·애셋
  접근도 보장한다. 본문 확보가 구성상 보장되므로 Skill 호출 여부는 검사하지 않는다.
  품질 변형(forced·without)에는 작업 도구(`Bash(*)`·Write·Edit)가 명시 허용된다 — 헤드리스
  기본 권한이 git 등 임의 명령을 거부해 실험군이 멈추는 실측 때문이고, 부작용 도구·MCP
  차단은 거부가 허용에 우선하므로 그대로다.
- `without` — 플러그인을 아예 싣지 않는다. 대조군이 대상 스킬의 훅·교리를 주입받은 채 답하면
  페어와이즈 델타가 구조적으로 눌린다(실측: superpowers baseline).

예외: 개인 스킬(`~/.claude/skills`)은 유저 스코프를 빼면 측정 대상 자체가 안 실려 cwd 격리만
받는다. `SKILL_EVAL_ALLOW_SIDE_EFFECTS=1`(MCP 스킬용)은 인자 격리를 끄되 **cwd 격리는
유지한다** — 런들이 폴더를 공유하면 앞 런의 산출물이 뒷 런의 전제("빈 폴더")를 깬다(실측).
Codex 런타임은 격리를 지원하지 않는다(`CODEX_HOME` 이 인증을 깨뜨린다 — 실측 401).
리포트가 실행의 격리 수준을 표시한다.

**도구 표면은 기본으로 좁혀서 실행된다.** 헤드리스 `-p`는 세션의 도구 레지스트리를 그대로
상속한다 — 실측에서 도구가 149개였고 그중 116개가 연결된 MCP 서버(Slack·Gmail·Notion·Drive의
쓰기 도구 포함)였다. 그래서 하네스가 `--strict-mcp-config`로 MCP를 끊고, 실행이 끝난 뒤에도
남는 일을 만드는 도구(`CronCreate`·`RemoteTrigger`·`PushNotification`·`Task`·`Workflow` 등)를
막는다. 남는 15개는 `Bash`·`Read`·`Write`·`Edit`·`Skill`·`WebSearch` 등 스킬이 일하는 데 필요한
것들이다. cwd 격리는 파일 접근만 좁히지 MCP 도달 범위는 안 좁히므로 둘 다 필요하다.

**MCP를 감싸는 스킬을 재려면** `SKILL_EVAL_ALLOW_SIDE_EFFECTS=1`로 이 차단을 푼다. 도구를
뺏은 채로 재면 "도구가 없어서 진 것"을 품질로 읽게 되기 때문이다. 이 경우 리포트에
`⚠ 부수효과 도구 허용` 경고가 붙고, 실행이 외부 시스템에 실제로 도달할 수 있다.

**예산 상한이 없다.** 케이스 5~7건 한 번 측정에 대략 \$2.6~4.6, `without` 단일 실행이
\$1.29까지 간 실측이 있다. 리포트의 `비용` 줄로 실제 지출을 확인한다.

**케이스마다 `split` 이 필수다.** `test` 가 판정 대상이고 `train` 은 튜닝용이다. 빠뜨리면
로드 시점에 에러가 난다 — 예전에는 조용히 `train` 이 되어 판정이 통째로 공회전했다.

## 당신이 판단할 것은 셋뿐이다

**0. `mine`은 그냥 기다린다.** 세션 로그를 훑은 뒤 원본 1건당 CLI를 한 번씩 불러 표현 변형을
만든다. 동시 4건씩 돌아서(`SKILL_EVAL_MINE_CONCURRENCY`로 조절) 보통 수십 초면 끝난다.
백그라운드로 돌리거나 별도의 대기 로직을 만들 필요가 없다.

**1. near-miss 선별.** `cases.draft.jsonl`을 읽고 변별력 있는 negative만 남긴다.
스킬과 아무 상관 없는 프롬프트("점심 메뉴 추천")는 통과시켜도 아무것도 검증하지 못하므로 버린다.
남길 것은 키워드가 겹치는데 실제로는 다른 처리가 맞는 애매한 것들이다.

**2. 실패 원인 진단.** 리포트의 실패 케이스를 보고 어느 쪽 문제인지 가른다.

- 오발동·미발동 → `description` 문제
- must/must_not 실패, 페어와이즈 패배 → SKILL.md 본문·참조 파일 문제

**단, 미발동을 곧바로 description 탓으로 돌리지 않는다.** 트리거 축은 2턴까지만 본다 —
정찰 한 턴은 허용되고 리포트의 "발동 시점" 줄이 즉시/정찰 후를 가르지만, 정찰을 두 턴 이상
끄는 프롬프트는 여전히 잘려 미발동으로 집계된다. 미발동 케이스는 원본 JSONL의 첫 응답을
열어 **모델이 스킬을 쓰겠다고 말했는지, 어떤 형제 스킬로 갔는지** 확인한 뒤에 판단한다.
정찰 절단은 측정 artifact 지만, 형제 스킬로 간 것은 진짜 라우팅 신호다(실측:
brainstorming 요청이 writing-skills 로 감 — 그건 description 을 고칠 근거가 맞다).

**3. `description` 재작성 제안.** 과잉 트리거면 범위를 좁히고, 미발동이면 왜·언제·어떻게를 보강한다.
하드코딩식 예외 나열이나 대문자 MUST/NEVER 남발이 아니라 "왜 이게 중요한지"를 설명하는 방향으로 쓴다.
특정 테스트 케이스에만 맞추면 과적합이다 — 목표는 보지 못한 프롬프트에서도 작동하는 것이다.

## 하지 않을 것

- **케이스를 `cases.jsonl`로 직접 승격하지 않는다.** draft에는 실사용 프롬프트 원문이 들어 있고 이 저장소는 공개다.
  후보를 정리해 보여주고 사람이 확정하게 한다.
- **SKILL.md를 직접 수정하지 않는다.** 제안까지만 한다.
- 리포트 숫자만 보고 결론짓지 않는다. 런 디렉터리(`<eval 홈>/evals/runs/<runId>/`)의 원본 JSONL을 열어 실행 과정을 확인한다.
  세 케이스 모두에서 비슷한 헬퍼를 새로 만들고 있다면 그 스킬에 스크립트를 번들해야 한다는 신호다.

## 결과 읽는 법

- **판정은 세 상태다.** `✓ 합격` · `✗ 불합격` · `? 판정 불가`. 판정 불가는 통과가 아니라
  **측정이 성립하지 않았다**는 뜻이다 — test 분모가 0이거나, 실행 에러로 빠진 test 케이스가
  있거나, 심판 자가진단이 수행되지 못한 경우다. 사유를 없앤 뒤 다시 돌려야 점수가 의미를 갖는다.
- **`권한 거부로 도구를 못 썼습니다`가 뜨면 스킬 탓이 아니다.** 헤드리스 실행은 권한이 필요한
  도구를 사람에게 묻지 않고 즉시 거부하고, 실행은 정상 종료한다(멈추지 않는다). 그 답변은
  "권한을 주세요"라서 규칙 검사에도 페어와이즈에도 쓸 수 없다 — 그래서 판정에서 뺀다.
  스킬이 그 도구를 정말 필요로 한다면 실행 환경의 권한 설정을 먼저 맞춰야 한다.
- **플러그인 스킬은 설치 없이도 측정된다 (Claude Code 런타임).** 격리 실행이 해석된 사본(체크아웃 우선)을 `--plugin-dir` 로 직접 로드하므로 발동 후보에 반드시 오른다. 개인 스킬과 Codex 런타임은 예전대로 세션에 설치·리로드되어 있어야 한다 — 안 돼 있으면 발동률 0%는 description 문제가 아니라 후보 목록에 없어서다.
- 실행 에러는 "발동 안 함"이 아니다. 에러율이 20%를 넘으면 그 실행 전체를 버리고 다시 돌린다.
- `unstable`(3회 중 2:1)은 평균보다 중요한 신호다. 그 케이스는 description이 경계에 걸쳐 있다는 뜻이다.
- **트리거 축 숫자는 런 간에 흔들린다.** 같은 코드·같은 케이스로 세 번 돌렸을 때 test positive
  발동률이 0% → 50% → 100% 를 왕복하고 판정이 뒤집힌 실측이 있다. 3회 다수결은 노이즈를
  거의 줄이지 못한다(참 발동확률 0.7인 케이스에서 판정 정확도 약 0.78). test positive가
  몇 건인지 먼저 보고, 두세 건뿐이라면 그 판정 줄은 신호가 아니라 잡음으로 취급한다.
  격리 도입으로 전역 스킬·훅과의 경쟁 오염은 제거됐지만(위 실측은 격리 전 값이다), 모델
  비결정성의 흔들림은 남는다.
- 페어와이즈 승률이 50% 근처면 **그 스킬은 존재 의미가 없다.** 개선이 아니라 폐기를 검토한다.
  단 baseline이 엉뚱한 주제로 샜다면 승리가 스킬의 우수함이 아니라 대조군의 실패를 뜻한다 —
  격리된 cwd에서 돌렸는지, `⚠ baseline` 경고가 붙지 않았는지 먼저 확인한다.
